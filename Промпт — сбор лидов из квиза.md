# Промпт для AI-агента: сбор данных из квиза → PostgreSQL → мини-CRM → Telegram

> Как пользоваться: целиком скопировать блок «ПРОМПТ» в Claude Code в пустой папке нового репозитория. Стек и модель данных согласованы с «ТЗ CRM VetPetCare v1.md» (NFR-10, раздел 9), чтобы потом это стало началом полной CRM, а не отдельным прототипом.

## ПРОМПТ

Ты — старший backend-разработчик. Построй первую версию системы сбора заявок для VetPetCare (онлайн-консультации ветеринаров и кинологов). Работай по шагам, после каждого шага запускай тесты и показывай, как проверить результат. Если чего-то не хватает для решения — задай вопрос, не выдумывай.

### 1. Цель

На сайте стоит квиз. Он собирает: **фамилию, имя владельца, номер телефона, вид питомца**. Квиз отправляет данные на наш сервер, сервер сохраняет их в PostgreSQL. Сотрудники смотрят заявки в простой веб-панели (мини-CRM). Новые заявки автоматически уходят уведомлением в Telegram.

Это первая версия будущей полной CRM VetPetCare. Она должна быть расширяемой, но в ней нет оплаты, расписания, анкет и бота для клиентов.

### 2. Стек (если нет веских причин менять)

- TypeScript, Node.js 20+.
- Next.js (App Router): и публичный API приема, и панель сотрудников в одном проекте.
- PostgreSQL 15+, миграции через Prisma или Drizzle (выбери один, объясни выбор в одной строке).
- Очередь фоновых задач на PostgreSQL (pg-boss) — для отправки в Telegram с повторными попытками.
- Валидация: zod.
- Тесты: vitest (юнит) + интеграционные тесты на реальном Postgres в Docker.
- Локальная разработка: `docker-compose.yml` с Postgres. Все секреты — в `.env`, в репозиторий попадает только `.env.example`.
- Продакшен: сервер в РФ (Yandex Cloud или Selectel), HTTPS, ежедневные бэкапы базы с хранением 30 дней. Подготовь `Dockerfile` и короткую инструкцию деплоя.

### 3. Поток данных

```
Квиз на сайте ──POST /api/leads──► Backend (валидация, нормализация, антиспам)
                                        │
                                        ├──► PostgreSQL (lead + client + patient + consent + audit)
                                        │
                                        └──► очередь (outbox) ──► Telegram
Сотрудник ──► Панель /crm (вход по email+пароль) ──► чтение/обработка заявок
```

### 4. Модель данных

Используй разделение владелец → животное, как в нашем ТЗ, даже если сейчас у животного одно поле. Все таблицы: `id` (uuid), `created_at`, `updated_at`. Время в UTC.

| Таблица | Поля |
|---|---|
| `clients` (владелец) | `last_name`, `first_name`, `phone` (нормализованный E.164), `phone_raw` (как ввел клиент), `email` (nullable), `telegram_user_id` (nullable, на будущее), `source` (`QUIZ`, `MANUAL`), `possible_duplicate` (bool), `merged_into_id` (nullable) |
| `patients` (животное) | `client_id`, `species` (вид), `name` (кличка, nullable), `breed`, `age_text`, `weight`, `notes` (все nullable — их заполнит анкета позже) |
| `leads` (заявка из квиза) | `client_id`, `patient_id`, `status` (`NEW`, `IN_PROGRESS`, `DONE`, `SPAM`), `assigned_to` (nullable → `users.id`), `quiz_version`, `raw_payload` (jsonb — полный исходный запрос), `utm` (jsonb: source/medium/campaign/content/term), `page_url`, `ip_hash`, `user_agent`, `idempotency_key` (unique), `comment` |
| `consents` | `client_id`, `type` (`PD_OFFER`, `MARKETING`), `granted` (bool), `document_version`, `granted_at`, `source` (`QUIZ`), `ip_hash` |
| `users` (сотрудники) | `email` (unique), `name`, `role` (`ADMIN`, `OWNER`), `password_hash`, `telegram_user_id` (nullable), `active` |
| `outbox` (события для интеграций) | `type` (например `lead.created`), `payload` (jsonb), `status` (`PENDING`, `SENT`, `FAILED`), `attempts`, `last_error`, `next_attempt_at` |
| `audit_log` | `actor` (user id или `system`), `entity`, `entity_id`, `action`, `before` (jsonb), `after` (jsonb), `at` |

Индексы: `clients(phone)`, `leads(status, created_at desc)`, `leads(idempotency_key)` unique.

Важно: храни фамилию и имя **отдельными полями**. Телефон — нормализованный; сырой ввод не теряем.

### 5. API приема заявок

`POST /api/leads`, JSON:

```json
{
  "last_name": "Иванова",
  "first_name": "Мария",
  "phone": "+7 (999) 123-45-67",
  "species": "собака",
  "consent_pd": true,
  "consent_marketing": false,
  "quiz_version": "2026-10-v1",
  "idempotency_key": "uuid, генерирует квиз при открытии",
  "utm": { "source": "...", "medium": "...", "campaign": "..." },
  "page_url": "https://..."
}
```

Правила:

1. **Валидация (zod):** фамилия, имя, телефон, вид — обязательны; строки обрезать, ограничить длину; `consent_pd` обязательно `true`, иначе 400. Ошибки — 400 с понятным списком полей.
2. **Нормализация телефона** в E.164 (библиотека `libphonenumber-js`, регион по умолчанию RU). Невалидный номер → 400.
3. **Вид питомца** — свободный текст или выбор из списка (собака, кошка, грызун, птица, другое) — сохраняй как пришло, но подготовь справочник значений для отчетов.
4. **Идемпотентность:** повторный запрос с тем же `idempotency_key` возвращает тот же результат и не создает дубль заявки (защита от двойного клика и ретраев).
5. **Поиск совпадений:** ищи существующего клиента по нормализованному телефону. Автоматически **ничего не склеивай**: если совпадение есть — создай новую карточку клиента с `possible_duplicate = true` и добавь пометку в заявку «возможный дубль: <id кандидатов>». Решение принимает человек (в ТЗ это запрещено автоматизировать).
6. **Транзакция:** клиент + животное + заявка + согласие + событие в `outbox` + запись в audit создаются в одной транзакции. Либо всё, либо ничего.
7. **Антиспам:** rate limit по IP (например, 10 заявок в час), honeypot-поле в квизе, ограничение размера тела запроса, опционально Cloudflare Turnstile / Yandex SmartCaptcha (оставь точку подключения). Подозрительные — статус `SPAM`, а не потеря данных.
8. **CORS:** разрешены только домены нашего сайта (список в `.env`).
9. **Ответ:** `201 {"lead_id": "...", "status": "created"}`. Без возврата чужих персональных данных.
10. **Логирование:** структурные логи с `lead_id`, без полных телефонов и ФИО в логах.

### 6. Мини-CRM (панель сотрудников)

Маршрут `/crm`, закрыт входом (email + пароль, хеш argon2/bcrypt, сессии с истечением, защита от перебора). Первого администратора создавай командой/сидом, а не регистрацией.

Экраны:

1. **Список заявок:** таблица (дата, фамилия и имя, телефон, вид питомца, статус, ответственный, метка «возможный дубль», UTM-источник). Фильтры по статусу, дате, источнику; поиск по телефону и ФИО; пагинация.
2. **Карточка заявки:** все поля, блок «возможные дубли» со ссылками на другие карточки, смена статуса, назначение ответственного, поле комментария, история действий (из audit_log).
3. **Выгрузка в CSV** (текущий фильтр).
4. Простая страница управления пользователями (только `OWNER`).

Права: проверять на сервере для каждого запроса, а не только в интерфейсе. Любое изменение статуса, ответственного, комментария пишется в `audit_log`.

Интерфейс на русском, адаптивный (должен нормально открываться с телефона).

### 7. Telegram

- Паттерн **outbox**: при создании заявки в транзакции записывается событие `lead.created`; фоновый воркер (pg-boss) читает события и отправляет сообщение через Telegram Bot API (библиотека grammY или прямой HTTP).
- Сообщение в общий чат администраторов: «Новая заявка: Фамилия Имя, телефон, вид питомца, источник, ссылка на карточку в CRM».
- Повторные попытки при ошибке: через 1, 5, 15 минут, затем статус `FAILED` и отметка в CRM (заявка не должна теряться, даже если Telegram недоступен).
- Реализуй отправку через абстракцию «канал доставки» (интерфейс `DeliveryChannel`), чтобы позже добавить email и другие каналы без переписывания сценариев.
- Токен бота и ID чата — только из переменных окружения.
- Бот работает в webhook-режиме; отдельный endpoint с проверкой секрета.
- На будущее (не делать сейчас): привязка клиента к боту по deep link `t.me/<bot>?start=<token>`, двусторонняя переписка.

### 8. Безопасность и персональные данные

- Собираем персональные данные → хостинг и бэкапы в РФ; в квизе обязателен чекбокс согласия с офертой и обработкой ПДн (со ссылками), маркетинговый — отдельный, необязательный, выключен по умолчанию. Сохраняй версию документа и время согласия.
- Секреты только в переменных окружения.
- Никаких персональных данных в URL и в логах.
- Резервные копии: скрипт `pg_dump` по расписанию + инструкция восстановления; проверь восстановление хотя бы раз.
- Подготовь короткую памятку: как удалить данные клиента по его запросу.

### 9. Тесты (обязательно)

- Юнит: нормализация телефона, валидация payload, поиск совпадений.
- Интеграция (реальный Postgres): создание заявки; повтор с тем же `idempotency_key` не создает дубль; телефон-дубль → `possible_duplicate`; отсутствие согласия → 400; откат транзакции при ошибке; rate limit.
- Права: сотрудник без входа не получает данные ни через UI, ни напрямую через API.
