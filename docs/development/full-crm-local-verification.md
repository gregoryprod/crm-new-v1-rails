# Полный интерфейс CRM на PostgreSQL — проверка 17.10.2026

База реализации: main `1ed5f831b86ffa2e1f470f7f23479964cb683a71`; локальная ветка `feat/full-crm-postgres`. Основной адрес `/crm/full`, корневой `/crm` ведёт туда. Публикация/merge этим локальным переключением не выполнялись.

## Сохранность

До изменений снят согласованный custom dump с SHA256 и manifest. Пробное восстановление в отдельную QA-базу подтвердило fingerprints всех 23 исходных таблиц. Перед окончательным переключением старое приложение остановлено; снят новый dump. После аддитивной миграции и импорта все 22 исходные public-таблицы совпали с ним по counts и fingerprints. Из исходных таблиц ожидаемо изменился только журнал Drizzle в схеме drizzle. Клиенты, исходная история, заявки и финансовые записи не перезаписывались.

Исторические проекции клиентов/врачей/аналитики импортированы в PostgreSQL с readback; канонические контакты и новые клиенты берутся из текущих таблиц. Все 6508 клиентов присутствуют. Исходные приватные JSON сохранены и больше не используются как писатель. В public нет клиентских JSON.

Резервные копии и приватные протоколы находятся вне Git в `private/crm-main/migrations/20261017-full-ui/` относительно клиентского workspace: `before/`, `final-before/`, `source-projections/`, `cutover-data-proof.json`, `live-http-result.json`. QA содержит дополнительного синтетического клиента; в рабочую базу он не добавлялся.

## Границы

Жизненный цикл, сегменты, когорты и ABC × XYZ описывают выгрузку на её дату среза. Текущие питомцы, приёмы и подтверждённые оплаты CRM показаны отдельно. Историческая стоимость не превращается в подтверждённую оплату, отсутствие данных по авансам не заменяется нулём.

Текущий календарь/обработка заявок открываются каноническими разделами. Старые JSON-шаблоны расписаний не объявляются реализованной функцией PostgreSQL-календаря. Подтверждённых смен в текущей базе ещё нет: свободные окна появятся после внесения реальных графиков, без выдуманных данных. Реальные приёмы, платежи или обращения для проверки не создавались.

## Возврат

Использовать сохранённую предыдущую сборку и текущую БД: остановить managed runtime из активного worktree, запустить прежнюю сборку с той же приватной конфигурацией. Новые таблицы не удалять. Восстановление dump поверх новых рабочих изменений требует отдельной сверки; автоматического разрушительного rollback нет.
