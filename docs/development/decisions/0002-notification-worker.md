# Решение 0002: worker уведомлений на outbox без pg-boss

Статус: предложено в задаче [#4](https://github.com/artemiyvladimirov-cmyk/vpc-crm/issues/4), ждёт ревью и приёмки. Дата: 2026-10-17.

## Контекст

Приём заявки уже пишет событие `lead.created` в таблицу `outbox` в той же транзакции, что и заявку (только `{"lead_id": …}`, без ПДн). Нужно доставить уведомление администраторам в Telegram отдельным процессом, с повторами через 1/5/15 минут, статусом `FAILED` и защитой от одновременной обработки. Архитектура предлагала pg-boss.

## Решение

Отдельный процесс `npm run worker` (`scripts/worker.ts` → `src/modules/notifications/worker.ts`) опрашивает существующую таблицу `outbox`. pg-boss не добавлен, миграций нет.

- **Захват (claim)** — один оператор: `UPDATE outbox … WHERE id = (SELECT … WHERE status='PENDING' AND next_attempt_at <= now() AND attempts < 4 ORDER BY next_attempt_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING …`. Он увеличивает `attempts` и сдвигает `next_attempt_at` на lease (120 с). Несколько worker не ждут друг друга и не берут одну строку.
- **Lease** — это `next_attempt_at`: пока он в будущем, событие не выдаётся. Если процесс упал во время отправки, событие снова станет доступным после lease. Lease больше максимального таймаута Telegram (60 с), один захват = одна отправка.
- **Fencing** — завершение (`SENT` или ошибка) обновляет строку только при `attempts` = значению из захвата и `status='PENDING'`. Опоздавший после потери lease worker ничего не перезапишет.
- **Повторы** — попытка 1 сразу; после ошибок 1, 2, 3 — пауза 60/300/900 с (не меньше `retry_after` от Telegram, максимум 1 ч); после ошибки 4-й попытки — `FAILED`. Прерванная последняя попытка после истечения lease переводится в `FAILED`, а не висит. «Заявка не найдена» и нераспознанное событие — сразу `FAILED`.
- **Время** — только часы PostgreSQL (`now()`), чтобы процессы на разных машинах не расходились.
- **Канал** — `DeliveryChannel.send(message)`; адресат (чат администраторов) — часть конфигурации канала. `TelegramChannel` вызывает Bot API `sendMessage` прямым HTTPS без SDK; текст без `parse_mode`, поэтому данные заявки не требуют экранирования.
- **Webhook не нужен**: бот только отправляет сообщения в чат администраторов, входящие обновления и клиентская переписка не обрабатываются. `TELEGRAM_WEBHOOK_SECRET` не вводится.

Почему не pg-boss: для одной очереди с фиксированным расписанием достаточно существующей таблицы, её индекса `(status, next_attempt_at)` и стандартного `SKIP LOCKED`. pg-boss добавил бы зависимость, собственную схему `pgboss` и второе хранилище состояния доставки, которое пришлось бы синхронизировать с `outbox`, где CRM уже показывает статус. Переход на pg-boss остаётся возможным, если появятся десятки типов задач, cron или приоритеты.

## Ограничение: at-least-once

Доставка «как минимум один раз». Если процесс остановится после того, как Telegram принял сообщение, но до записи `SENT` (или ответ не пришёл из-за таймаута), событие будет отправлено повторно после lease: в чате появится дубль. Exactly-once не обещается: у Bot API `sendMessage` нет ключа идемпотентности. Потеря события исключена: оно остаётся в `outbox` до `SENT`/`FAILED`.

## Секреты

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_CHAT_ID` читает только worker (zod; в ошибках только имена переменных). Токен есть лишь в URL запроса. В `outbox.last_error` и CRM попадает короткое описание (`Telegram HTTP 429: …`, таймаут, сетевая ошибка) после удаления всего, что похоже на токен; тексты ошибок fetch не сохраняются. В логи пишутся только id события, номер попытки и исход.
