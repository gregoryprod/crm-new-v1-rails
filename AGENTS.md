# Правила разработки CRM VetPetCare

Эти правила общие для Codex, Claude Code и других исполнителей. Отвечай по-русски, обращайся к владельцу на «ты». CLAUDE.md импортирует этот файл; второй набор правил не заводи.

## Как общаться с владельцем

Владелец (Артём) не разбирается в разработке. Отвечай ему максимально простым, нетехническим языком:

- Объясняй, что изменилось для бизнеса и для него лично, а не как это устроено внутри.
- Избегай терминов (PR, merge, SHA, CI, миграция, worktree, Docker и т. п.). Если без слова не обойтись — сразу поясни его бытовым сравнением.
- Сначала короткий итог в одну-две фразы, затем детали только при необходимости.
- Когда нужно его решение, формулируй вопрос так, чтобы на него можно было ответить «да/нет» или выбором из вариантов, и объясняй последствия каждого варианта.
- Если он должен что-то сделать сам, давай пошаговую инструкцию: куда нажать и что ввести.

Это правило относится к общению с владельцем. Технические записи в issue, PR, checkpoint и Beads по-прежнему ведутся в принятом формате.

## Вход и восстановление работы

На новом компьютере или при смене ответственного сначала прочитай [HANDOFF.md](HANDOFF.md): восстанови общий контекст/Beads и проверь полномочия единственного писателя. Согласованные роли следующего этапа указаны в `docs/development/handoff/team.json`; это описание команды, не автоматический runner. Датированный снимок и предлагаемые этапы v1 не заменяют живые контракты и текущие статусы.

1. Прочитай README.md, [закреплённый контекст #7](https://github.com/artemiyvladimirov-cmyk/vpc-crm/issues/7), выбранный issue с комментариями и его зависимости. Контекст можно найти через label `context`; он остаётся открытым и не является задачей исполнения.
2. Выполни `python3 scripts/beads.py prime`, затем `ready` и `show ID --json` для выбранной задачи. Проверенный CLI-помощник выбирает только базу `vpc-crm` этого Git-репозитория, включая linked worktree; сырой `bd` может найти родительскую базу клиента. При отсутствии локальной базы сначала прочитай [Beads](docs/development/beads.md).
3. Сверь HEAD/ветку и `git status`, связанные PR, CI и последний checkpoint. Датированный снимок в контексте не заменяет текущую проверку. Изменения в открытом PR не считай доступными в main или production.
4. Перед продолжением установи разрешённую цель, владельца файлов, исполнителя, независимого проверяющего и следующий проверяемый шаг. Если GitHub недоступен, используй последний сохранённый checkpoint, явно обозначь его дату и не объявляй удалённые статусы подтверждёнными.

## Источники и границы

- Beads — долговременная агентская очередь: задачи, claim, статусы, зависимости и найденные follow-up. GitHub issue по `external_ref` — контракт, приёмка и доступная человеку история; context issue — навигация; Projects — проекция тех же задач. PR и CI доказывают результат. Два независимых backlog не заводи; оркестратор согласует изменения и сохраняет checkpoint в обеих системах. `.orchestration/` и чат не заменяют общую память.
- Для v0.1 используй «Архитектура CRM — сбор лидов из квиза.md» и «Промпт — сбор лидов из квиза.md». Для полной v1 — «ТЗ CRM VetPetCare v1.md». «VetPetCare — путь клиента и алгоритмы CRM.md» — исходный контекст; при расхождениях приоритет у ТЗ v1. Открытый вопрос не превращай в согласованное требование.
- Сделано: лиды из квиза, панель персонала, уведомления администраторам, расписание с записью, ручная фиксация оплат, рабочее пространство, импорт YClients (подробно — PRD). Следующие этапы: роль специалиста, очередь ручной обработки, виджет с ЮKassa, клиентский бот, анкеты и выписки (roadmap).
- Стек: Ruby on Rails 8.1, PostgreSQL 17, Hotwire (без собственного JavaScript), деплой Kamal 2 — [решение 0003](docs/development/decisions/0003-rails-and-kamal.md), заменяет решение 0001 (Next.js + Drizzle). Как устроен код и правила проекта — [rails-guide](docs/development/rails-guide.md). Не добавляй инфраструктуру без необходимости.
- Продукт: [PRD](docs/product/PRD.md) (что сделано и где в коде) и [roadmap](docs/product/roadmap.md). Типовые сценарии — skills в `.claude/skills/` (`crm-feature`, `crm-schema-change`, `crm-verify`, `crm-deploy`, `crm-yclients-import`, `crm-data-safety`; общие по Rails — `rails-guides`, `rails-testing`, `rails-kamal-deploy`): прочитай нужный `SKILL.md` перед работой.

## Владелец, оркестратор и исполнители

- Владелец задаёт цель, приоритет, scope и ограничения; принимает результат и отдельно разрешает merge/production. Его действующие полномочия не нужно запрашивать повторно.
- Оркестратор ведёт Issues/Projects, декомпозирует разрешённую цель, проверяет зависимости, выбирает Ready-задачу внутри этой цели, назначает исполнителя и независимого проверяющего, проверяет доказательства и обновляет общую память. Декомпозиция не расширяет поручение.
- Одна исполняемая задача — один законченный сценарий, владелец файлов и критерий приёмки. Эпик — контейнер дочерних задач с label `epic`; не запускать его одновременно с теми же дочерними работами.
- Параллельно разрешены максимум две независимые задачи с непересекающимися файлами/контрактами в разных worktree. Общие миграции и API-контракты выполняет один ответственный. Проверяющий не редактирует результат исполнителя; по умолчанию выбирай другой инструмент или Human.
- Пишет в общую Beads-базу только оркестратор, последовательными командами. Исполнители читают назначенную задачу и возвращают результат; embedded Dolt не является распределённой блокировкой между клонами. Перед claim сверяй полномочия/зависимости и делай Dolt pull; после изменения — push. Конфликт статусов сначала разреши по доказательству события, а не перезаписью вслепую.
- Worker в Projects обозначает инструмент, assignee — ответственного человека. Назначение не запускает агента и не выдаёт доступ к провайдеру, секретам или production. OpenCode/DeepSeek подключают только в явно разрешённых условиях; модель и провайдер записываются в checkpoint.

## Одна задача — одна ветка

1. Проверь текущую ветку, `git status`, зависимости задачи и область ответственности. Не перезаписывай чужие изменения.
2. Для независимой задачи используй отдельную ветку и worktree. Сначала зафиксируй физический путь и базовый SHA. Worktree разделяет изменения; доступ к файлам и сети ограничивается отдельно.
3. В задаче укажи исполнителя, независимого проверяющего и файлы/модули, которыми владеет исполнитель. Параллельные изменения общей схемы БД и API-контрактов сначала согласуй.
4. Реализуй узкий полный сценарий, проверяемый по критериям задачи. Не включай соседние улучшения.
5. Прогони проверки, перечисли измененные файлы, SHA и оставшиеся ограничения. Не объявляй задачу выполненной только по отчету модели.
6. Создай PR со ссылкой на issue. Для подготовки PR в рамках порученной задачи отдельное подтверждение не нужно; merge и production-деплой требуют прямой команды владельца.

## Общая память и завершение сессии

- Beads-состояния: `backlog` → `open` (Ready) → `in_progress` → `review` → `closed`; `blocked` — конкретный блокер. `bd ready` предлагает только разрешённый `open` без блокирующих связей; право начать работу отдельно проверяет оркестратор. Контекст не исполняется, эпики — только контейнеры. Новые неразрешённые follow-up сразу переводи в `backlog`.
- В начале работы оставь в issue запись о выбранной задаче, исполнителе/проверяющем, файлах, worktree, base SHA и ограничениях. При прерывании, блокере, передаче и завершении добавь checkpoint по формату из [workflow](docs/development/workflow.md).
- В комментарии Beads сохрани краткий checkpoint со ссылкой на GitHub checkpoint; закончи сессию Dolt commit/push и проверь результат. `review` не закрывай: `closed` для кода/правил только после принятия и прямо разрешённого merge, как `Done` на доске. JSONL — переносимый export, а не sync/backup.
- Checkpoint содержит фактически сделанное, ветку и head SHA, команды/результаты, ограничения и следующий конкретный шаг. Для незафиксированных правок перечисли файлы: по одному SHA их восстановить нельзя.
- Решения о scope и процессе записывай с причиной и ссылкой на доказательство в context issue; технические решения о коде — в ADR, связанном с issue/PR. При замене решения сохраняй ссылку на предыдущую версию. Не копируй backlog и сырые логи в контекст.
- Оркестратор обновляет статус после проверенного события. Review — результат ожидает приёмки или merge; Done для кода — только после разрешённого merge и закрытия issue. Context и эпики исключены из очереди Ready; PR не вторая задача исполнения.

## Приемка и ревью

- Проверяющий читает требования, реальный diff и нужные исходники. Ревью относится к конкретному SHA, не меняет код и не является самооценкой исполнителя.
- После исправлений повтори затронутые проверки и ревью для нового SHA. Максимум два цикла автоматического исправления; затем объясни блокер владельцу.
- Замечание содержит приоритет, файл/строку, воспроизводимую причину и требуемое исправление. Решение проверяющего не заменяет успешные проверки.
- До merge нужны все обязательные проверки и независимое ревью. Если защиты ветки или доступа к проверяющему нет, явно укажи ограничение; не имитируй approval.
- Текущие команды проверок указаны в README. Для приложения добавь проверки типов, линтер, тесты и сборку одновременно с каркасом. Для транзакций/идемпотентности тестируй на реальном PostgreSQL.
- Интерфейс проверяй в измененном сценарии; данные — повторным чтением; релиз — по живому адресу в пределах разрешенного запроса.

## Данные и секреты

- Не коммить `private/`, `export/`, `База/`, `data/`, `.env*` с секретами, клиентские CSV/XLSX, БД, транскрипты и сырые переписки. `.env.example` содержит только пустые значения или явно синтетические примеры.
- В issue, PR, CI и логи не помещай ФИО клиентов, телефоны, ответы анкет, документы и токены. Для тестов используй синтетические данные, создаваемые тестом.
- `merge-duplicates.ps1` — локальный аналитический инструмент. Его вероятные совпадения не являются разрешением на автоматическое слияние в CRM или импорт производной таблицы как канонической базы.
- Не запускай авторизацию/выгрузку из Yclients и не читай реальные выгрузки без поручения на работу с этими данными. Не подключай production credentials к агентскому окружению или CI.
- Коммит перед push проверяй командой `python3 scripts/check-repository-data.py`. `.gitignore` не защищает уже отслеживаемые файлы и не заменяет проверку содержимого.
- Расчеты выполняй JavaScript; для финансовых показателей фиксируй период, формулу, единицы и источник. Не называй стоимость записи подтвержденной выручкой.

## Внешние действия

Публикация, production, реальные платежи/возвраты, запуск бота и отправка сообщений клиентам — только по прямой команде. Настройка задач и PR не разрешает эти действия. Для тестов доставки используй заглушку или отдельно разрешенный тестовый чат.

Общие правила и схемы результатов хранятся в репозитории; локальные логи и служебное состояние — в игнорируемой `.orchestration/`. Автоматического runner в исходной версии пока нет.
